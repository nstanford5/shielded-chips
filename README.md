# Shielded Chips

This project is built on the Midnight Network.

A worked example of **shielded tokens** in [Compact](https://docs.midnight.network):
a house mints casino chips as a shielded token, players bet those chips on a
RED/BLACK roulette wheel, and winners are paid 2× — with chip holdings carried
inside zswap UTXOs rather than in a public balance map, and no player's wallet
identifiable from the chain.

The interesting part is the token plumbing: minting a coin, sending it to a
wallet, receiving it into a contract, custodying it, and spending it back out —
and, more subtly, doing all that without leaving a coin nonce in public state,
which would be enough to unmask the wallets involved. The game itself is
deliberately simple so the coin operations stay in focus.

A step-by-step walkthrough of both contracts lives in [`TUTORIAL.md`](./TUTORIAL.md).

## What it demonstrates

- **[MIP-0011](https://github.com/midnightntwrk/midnight-improvement-proposals/blob/main/mips/mip-0011-native-shielded-token.md)
  conformance** — `chips.compact` implements the Native Shielded Token Standard
  (Fungible profile, supply-accounting extension): metadata, `_mint`, and both
  burn variants with the correct Zswap spend path for each
- `mintShieldedToken` — creating coins with a caller-supplied *secret* nonce, the
  recipient-private mint
- `sendShielded` — paying a coin out to a wallet or a contract
- `receiveShielded` + `Map.insertCoin` — a contract taking custody of an incoming coin
- `ShieldedCoinInfo` vs `QualifiedShieldedCoinInfo`, and `Either<ZswapCoinPublicKey, ContractAddress>` recipients
- Deriving a per-dapp pseudonym from a witness secret so wallet identity never hits the chain
- **Keeping coin nonces out of public state** — commitment-based escrow, plus
  `mergeCoin` argument order, so neither the wallet that funds a bet nor the
  wallet that gets paid can be identified. This is the subtle part; see
  [Privacy model](#privacy-model).
- A commit/reveal on the winning number
- Both MIP-0011 burn paths: transient (`sendImmediateShielded`) for a same-tx coin, Merkle (`sendShielded`) for a contract-held one
- Access control on the whole supply-changing surface, via a proof-bound
  commitment check rather than `ownPublicKey()`
- Wiring two contracts together from TypeScript: separate compiled artifacts, separate ZK config paths, one shared witness

## Layout

```
contract/
  chips.compact        # MIP-0011 native shielded token; only the house can mint
  roulette.compact     # RED/BLACK game; custodies chip coins, pays 2x
  index.ts             # CompiledContract wiring for both contracts
  witnesses.ts         # localSecretKey (shared) + escrow witnesses for roulette
  managed/             # generated by `yarn compile` (gitignored)
src/
  config.ts            # network endpoints (local devnet)
  providers.ts         # wallet + proof server + indexer + ZK config per contract
  wallet.ts            # MidnightWalletProvider and a wallet-sync helper
  test/roulette.test.ts # end-to-end round against a local devnet
compose.yml            # node + indexer + proof server
```

## Prerequisites

- Node.js ≥ 22 (`engines` in `package.json`)
- Yarn 1.22 (`packageManager` is pinned)
- Docker with the Compose plugin, for the local devnet
- The [Compact toolchain](https://docs.midnight.network) with a compiler
  supporting `language_version 0.23` (`compact check` reports what you have)

## Quick start

```bash
yarn install
yarn compile      # writes contract/managed/{chips,roulette}
yarn validate     # devnet up -> run the e2e test -> devnet down
```

`yarn validate` is the one-shot path. To keep the devnet running between
iterations, do it in steps instead:

```bash
yarn env:up       # docker compose up -d --wait
yarn test:local   # MIDNIGHT_NETWORK=local vitest run
yarn env:down
```

Proof generation dominates the runtime — the full suite is roughly 7 minutes of
wall clock, and the vitest timeouts are set high (15 min per test) to match.
Set `LOG_LEVEL=debug` for verbose wallet-sync output.

### Scripts

| Script | What it does |
|---|---|
| `yarn compile` | Compiles both `.compact` files into `contract/managed/<name>` |
| `yarn env:up` / `yarn env:down` | Starts / stops the local devnet from `compose.yml` |
| `yarn test` | Runs vitest (expects a network per `MIDNIGHT_NETWORK`) |
| `yarn test:local` | `yarn test` against the local devnet |
| `yarn validate` | `env:up`, then `test:local`, then `env:down` regardless of result |

`src/config.ts` only knows the `local` network today; any other value of
`MIDNIGHT_NETWORK` throws.

## How a round plays out

The e2e test in `src/test/roulette.test.ts` walks the whole flow with three
wallets — Alice (the house), Bob, and Claire:

1. Alice deploys `chips.compact` (name/symbol/decimals/domain fixed at
   construction) and mints 100-chip coins with fresh random nonces: two to
   herself (to back payouts), one to Bob, one to Claire.
2. Alice deploys `roulette.compact`, binding it to the chip token's color, and
   commits to the winning number (`persistentHash(num, sk)`).
3. Alice deposits her two match coins with `houseDeposit`.
4. Bob re-nonces his chips with a self-transfer first (see
   `splitShieldedCoin`), then bets RED; Claire bets BLACK. Each sends their
   chip coin into the contract, which takes custody but records only a
   *commitment* to the coin under their pseudonym.
5. Alice calls `revealWinningNumber(1)`; 1 is RED on a single-zero wheel, so Bob wins.
6. Bob claims 2× in a single `claimWinnings(matchKey)` call. It reopens his
   escrow commitment from private state and merges his coin with one of
   Alice's match coins, paying out one coin worth 2×.
7. Claire calls `forfeit()`, moving her losing coin into the house pool — only
   she can, because only she can reopen her commitment. Alice then sweeps both
   pool coins (the forfeit and the unused match) with `houseClaimMatch`.
8. Both MIP-0011 burn paths run, and both are house-only: Alice burns half a
   swept coin via the transient path, and mints into the chips treasury and
   burns part of it via the Merkle path, with the change persisted rather than
   stranded. Bob's attempts to mint or burn are rejected.

The 2× math is enforced on chain: `claimWinnings` asserts the match coin's value
equals `betValues[player]`, and both `betColor` and `houseDeposit`
require the incoming coin's color to equal the chip color locked in at deploy
time. Neither side has to trust the other off chain.

## Privacy model

This example is deliberately **identity-private, behavior-public**.

### The rule that drives the design

A coin commitment is a deterministic function of `(nonce, color, value, owner)`,
and every coin derived from a coin — via `sendShielded` or `mergeCoin` — has a
nonce that is a deterministic function of the source nonce alone. Nothing about
the recipient enters it.

So **any coin nonce in public ledger state is a linkability oracle**. Given a
guessed wallet key, anyone can recompute the commitment and get a yes/no answer,
in both directions:

- *inbound* — which wallet funded the coin that was escrowed;
- *outbound* — which wallet was paid from it, since the payout nonce follows
  from the escrow nonce.

An unrelated `sk` for the pseudonym is necessary but nowhere near sufficient. A
pseudonym is only as private as the coins recorded under it. Two consequences
shape this code:

1. `chips.compact` takes the mint nonce as a caller-supplied random value and
   keeps no nonce state on chain at all. This is MIP-0011's base `_mint`, the
   *recipient-private* mint. Its optional derived-nonce extension keeps a nonce
   chain in public ledger state and is documented by the standard itself as
   *recipient-public*, because the commitment can then be recomputed by
   enumerating candidate recipient keys — so this contract does not use it.
2. `roulette.compact` stores a `persistentCommit` of the escrowed coin instead
   of the coin itself, and `claimWinnings` passes the player's secret escrow
   coin as `mergeCoin`'s **first** argument, because the merged nonce is derived
   from the first input. Merging the other way round would derive the payout
   nonce from a house coin sitting in public state, and the winner could be
   identified.

### What is private

- The player's wallet identity, both when betting and when being paid.
- The escrowed coin — its nonce, and therefore every coin derived from it.
- Chip *balances*, which live in zswap UTXOs.
- The winning number, until it is revealed.

### What is public

- The pseudonym, once a player acts, and everything it does *within* this
  contract: the bet color, the bet size (`betValues`), and whether it won.
  Behavior is readable; who did it is not.
- The chip color, and every value in `houseCoins`.
- **Mint amounts.** `mintShieldedToken` records the amount in the transaction's
  `Effects.shielded_mints` so the ledger can track supply. Minting hides the
  recipient, not the amount. Transferring an already-minted coin hides both.
- **The house's wallet key** is confirmable, because it sweeps the pool coins
  whose nonces are public. Accepted here: the house is publicly identified by
  `theHouse` anyway. A player-facing contract should not expose a participant
  this way.

### Residual: the chip issuer

The issuer knows the exact coin it minted you. If you bet that coin untouched,
the issuer alone — nobody else — can still recognise it. `splitShieldedCoin` in
`src/wallet.ts` self-transfers first, replacing the coin with one whose nonce is
wallet-chosen randomness the issuer has never seen. The e2e test does this for
Bob and asserts the nonce actually changes.

Hiding the bet value or color too would mean committing those as well and
re-proving them on claim, the same shape as the escrow commitment.

## Caveats

This is teaching code, not production code:

- The house holds the reveal secret and can decline to reveal.
- Match coins must be pre-deposited by the house at exactly the bet denomination.
- There is a single round per deployment. The pseudonym derivation mixes in only
  a constant string, so the same `sk` yields the same pseudonym in every
  deployment — mix in `kernel.self()` if you need per-table unlinkability.
- A losing player must call `forfeit()` for the house to recover the stake. That
  is the price of keeping the escrowed coin out of public state: only the player
  can reopen their own commitment. A production design needs an incentive (or a
  bond) to make forfeiting rational.
- `sk` does triple duty — dapp identity, mint authority, and the blinding factor
  for `winningNumHash`. Revealing the commitment opening to prove fairness would
  also hand over mint authority. Use a separate blinding witness.
- Mint amounts are capped at `Uint<64>` by the ledger (`shieldedMints` is a
  `u64` map), so larger issuance needs multiple mints.
- `totalSupply` is an upper bound, not a measurement: coins can be destroyed
  without involving the contract, so exact circulating supply is unknowable.
- The test seeds are fixed, well-known values.
