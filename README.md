# Shielded Chips

This project is built on the Midnight Network.

A worked example of **shielded tokens** in [Compact](https://docs.midnight.network):
a house mints casino chips as a shielded token, players bet those chips on a
RED/BLACK roulette wheel, and winners are paid 2× — with every chip value
carried inside zswap UTXOs rather than written to public ledger state.

The interesting part is the token plumbing: minting a coin, sending it to a
wallet, receiving it into a contract, custodying it in a ledger `Map`, and
spending it back out. The game itself is deliberately simple so the coin
operations stay in focus.

A step-by-step walkthrough of both contracts lives in [`TUTORIAL.md`](./TUTORIAL.md).

## What it demonstrates

- `mintShieldedToken` + `evolveNonce` — creating coins with fresh, deployment-bound nonces
- `sendShielded` — paying a coin out to a wallet or a contract
- `receiveShielded` + `Map.insertCoin` — a contract taking custody of an incoming coin
- `ShieldedCoinInfo` vs `QualifiedShieldedCoinInfo`, and `Either<ZswapCoinPublicKey, ContractAddress>` recipients
- Deriving a per-dapp pseudonym from a witness secret so wallet identity never hits the chain
- A commit/reveal on the winning number
- Wiring two contracts together from TypeScript: separate compiled artifacts, separate ZK config paths, one shared witness

## Layout

```
contract/
  chips.compact        # shielded chip token; only the house can mint
  roulette.compact     # RED/BLACK game; custodies chip coins, pays 2x
  index.ts             # CompiledContract wiring for both contracts
  witnesses.ts         # localSecretKey witness, shared by both
  managed/             # generated by `yarn compile` (gitignored)
src/
  config.ts            # network endpoints (local devnet)
  providers.ts         # wallet + proof server + indexer + ZK config per contract
  wallet.ts            # MidnightWalletProvider and a wallet-sync helper
  test/roulette.test.ts # end-to-end round against a local devnet
compose.yml            # node + indexer + proof server
```

## Prerequisites

- Node.js ≥ 22 (`engines` in `package.json`)
- Yarn 1.22 (`packageManager` is pinned)
- Docker with the Compose plugin, for the local devnet
- The [Compact toolchain](https://docs.midnight.network) with a compiler
  supporting `language_version 0.23` (`compact check` reports what you have)

## Quick start

```bash
yarn install
yarn compile      # writes contract/managed/{chips,roulette}
yarn validate     # devnet up -> run the e2e test -> devnet down
```

`yarn validate` is the one-shot path. To keep the devnet running between
iterations, do it in steps instead:

```bash
yarn env:up       # docker compose up -d --wait
yarn test:local   # MIDNIGHT_NETWORK=local vitest run
yarn env:down
```

Proof generation dominates the runtime — a full round is roughly 6 minutes of
wall clock, and the vitest timeouts are set high (15 min per test) to match.
Set `LOG_LEVEL=debug` for verbose wallet-sync output.

### Scripts

| Script | What it does |
|---|---|
| `yarn compile` | Compiles both `.compact` files into `contract/managed/<name>` |
| `yarn env:up` / `yarn env:down` | Starts / stops the local devnet from `compose.yml` |
| `yarn test` | Runs vitest (expects a network per `MIDNIGHT_NETWORK`) |
| `yarn test:local` | `yarn test` against the local devnet |
| `yarn validate` | `env:up`, then `test:local`, then `env:down` regardless of result |

`src/config.ts` only knows the `local` network today; any other value of
`MIDNIGHT_NETWORK` throws.

## How a round plays out

The e2e test in `src/test/roulette.test.ts` walks the whole flow with three
wallets — Alice (the house), Bob, and Claire:

1. Alice deploys `chips.compact` and mints 100-chip coins: two to herself (to
   back payouts), one to Bob, one to Claire.
2. Alice deploys `roulette.compact`, binding it to the chip token's color, and
   commits to the winning number (`persistentHash(num, sk)`).
3. Alice deposits her two match coins with `houseDeposit`.
4. Bob bets RED, Claire bets BLACK — each sends their chip coin into the
   contract, which stashes it under their pseudonym.
5. Alice calls `revealWinningNumber(1)`; 1 is RED on a single-zero wheel, so Bob wins.
6. Bob claims 2× in two calls: `claimMyBet()` returns his own coin, then
   `claimMatch(key)` sends one of Alice's match coins. The split is required —
   a single circuit doing both blows the node's per-circuit coin-effects budget.
7. Alice sweeps the leftovers: `houseClaimBet` takes Claire's losing coin and
   `houseClaimMatch` takes the unused match coin.

The 2× math is enforced on chain: `claimMatch` asserts the match coin's value
equals the claimant's original bet, and both `betColor` and `houseDeposit`
require the incoming coin's color to equal the chip color locked in at deploy
time. Neither side has to trust the other off chain.

## Privacy model

This example is deliberately **identity-private, behavior-public**:

- **Private** — the player's wallet identity. On-chain they appear as
  `persistentHash(["roulette:pk:", sk])` where `sk` is a witness-supplied
  secret unrelated to their wallet keys. The domain separator also prevents
  linking the same player across dapps.
- **Private** — chip *balances*, which live in zswap UTXOs, and the winning
  number until it is revealed.
- **Public** — the pseudonym (once a player acts), the bet color, the bet's
  coin value in `betCoins`, the chip color, and the win/loss record. An
  observer can follow a single pseudonym's behavior within the contract.

Hiding the bet value or color as well would mean replacing the public maps with
commitment-based storage and reconstructing coin info from witnesses at claim
time — a substantial refactor, out of scope here.

## Caveats

This is teaching code, not production code. The house holds the reveal secret
and can decline to reveal; match coins must be pre-deposited by the house at
exactly the bet denomination; there is a single round per deployment; and the
test seeds are fixed, well-known values.
